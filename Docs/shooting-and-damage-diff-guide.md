# От наведения к законченному циклу выстрела

## Основа сравнения

Материал описывает незакоммиченные изменения рабочего дерева относительно коммита `83ca56f` (`mouse shooting + projectile`). В исходном варианте уже существовали:

- наведение пушки на указатель мыши;
- отражение спрайта пушки при прицеливании влево;
- метод `Shoot()`, создающий снаряд из центра пушки;
- прямолинейное движение и автоматическое удаление снаряда;
- получение игроком урона при физическом столкновении с зомби.

При этом выстрел ещё не вызывался пользовательским вводом, боезапаса и попаданий по врагу не было, а `Zombie` содержал только величину контактного урона.

Шесть новых файлов пока не добавлены в индекс Git: `AmmoUI.cs`, `AmmoUI.cs.meta`, `EnemyHp.cs`, `EnemyHp.cs.meta`, `EnemyHit.anim` и `EnemyHit.anim.meta`. Обычный `git diff` их не показывает, но без них описание текущего состояния было бы неполным. Особенно важны `.meta`: они сохраняют GUID, на которые уже ссылаются сцена, префаб и Animator Controller.

## Цель изменений

Изменения превращают отдельные заготовки в связанную игровую цепочку:

```text
движение мыши
    → поворот пушки и направление персонажа
    → нажатие кнопки при наличии патронов
    → создание снаряда у конца ствола и звук
    → попадание снаряда в зомби
    → уменьшение HP
    → обновление шкалы, анимация и частицы
    → уничтожение зомби при нулевом HP
```

Ниже изменения расположены не в файловом порядке diff, а в порядке, в котором их логично внедрять и проверять.

## Шаг 1. Передать управление направлением персонажа системе прицеливания

Раньше `PlayerMovement` отражал персонажа на основании горизонтального движения. Теперь этот код закомментирован, потому что направление взгляда определяется положением мыши, а не клавишами перемещения. Одновременно удалён отладочный `print`, выполнявшийся каждый кадр.

Старая ответственность:

```csharp
if (movement.x < 0f)
{
    sr.flipX = true;
}
else
{
    sr.flipX = false;
}
```

Новая ответственность находится в `MouseShoting.RotateToMouse()`:

```csharp
sr.flipY = aimDirection.x < 0;
playerSr.flipX = aimDirection.x < 0;
```

Пушка отражается по `Y`, поскольку она уже повёрнута вокруг оси `Z`. Персонаж отражается по `X`. Оба решения используют один признак — находится ли указатель слева от пушки.

В текущей иерархии `Gun` является непосредственным ребёнком `Player`, поэтому ссылка берётся так:

```csharp
playerSr = transform.parent.GetComponent<SpriteRenderer>();
```

Это исправляет ошибку варианта с `GetComponentInParent<SpriteRenderer>()`: такой поиск сначала проверяет объект пушки и может вернуть её собственный `SpriteRenderer`. Однако непосредственный доступ через `transform.parent` всё ещё зависит от структуры иерархии. Для развиваемого проекта устойчивее сериализованная ссылка:

```csharp
[SerializeField] private SpriteRenderer playerRenderer;
```

После этого нужный объект явно назначается в Inspector.

### Проверка шага

Персонаж должен смотреть в сторону курсора даже при движении в противоположную сторону. При пересечении вертикальной линии у `Gun` должен изменяться только `flipY`, а у `Player` — только `flipX`. В текущем коде нет мёртвой зоны около `aimDirection.x == 0`, поэтому при очень точном движении курсора около вертикали направление персонажа может дрожать.

## Шаг 2. Ввести состояние боезапаса и его отображение

В `Farmer` добавлены количество патронов и ссылка на новый компонент `AmmoUI`:

```csharp
[SerializeField] private int bullets;
[SerializeField] private AmmoUI ammoUI;

public int Bullets => bullets;
```

Состояние изменяется через один публичный метод:

```csharp
public void ChangeBullets(int amount)
{
    bullets += amount;
    ammoUI.UpdateAmmo(bullets);
}
```

`AmmoUI` не хранит боезапас, а только отображает переданное значение:

```csharp
public class AmmoUI : MonoBehaviour
{
    [SerializeField] private TMPro.TextMeshProUGUI ammoText;

    public void UpdateAmmo(int ammo)
    {
        ammoText.text = ammo.ToString();
    }
}
```

Это важное разделение: `Farmer` является источником игрового состояния, а `AmmoUI` — представлением. В `Farmer.Start()` начальные HP и патроны сразу передаются интерфейсу:

```csharp
private void Start()
{
    healthUI.UpdateHp(hp);
    ammoUI.UpdateAmmo(bullets);
}
```

В сцене для этого добавлен блок `Ammobox` с изображением и `AmmoText`, ссылка на `AmmoUI` назначена игроку. Текущее тестовое значение боезапаса в сцене — `222`.

### Проверка шага

После запуска значение в UI должно совпадать с `Farmer.bullets`. Изменение боезапаса через `ChangeBullets()` должно немедленно обновлять текст.

## Шаг 3. Собрать пользовательский сценарий выстрела

В `MouseShoting.Update()` добавлена проверка левой кнопки мыши и доступности патронов:

```csharp
if (player.Bullets > 0 && Input.GetMouseButtonDown(0))
{
    Shoot();
    audioSource.Play();
    player.ChangeBullets(-1);
}
```

Одна ветка успешного выстрела теперь последовательно выполняет три видимых действия: создаёт снаряд, воспроизводит звук и списывает один патрон. Если патронов нет, ни одно из этих действий не выполняется.

В сцене на `Gun` добавлен `AudioSource` с назначенным аудиоклипом и отключённым `Play On Awake`.

### Что важно сохранить

Проверка боезапаса должна происходить до создания снаряда. Если позднее появятся перезарядка, темп стрельбы или разные виды оружия, лучше перенести проверку и списание внутрь одного метода вроде `TryShoot()`, чтобы другие вызывающие стороны не могли забыть снять патрон.

```csharp
private bool TryShoot()
{
    if (player.Bullets <= 0)
        return false;

    Shoot();
    audioSource.Play();
    player.ChangeBullets(-1);
    return true;
}
```

## Шаг 4. Создавать снаряд у конца ствола

В сцене появился дочерний объект `Gun/Muzzle`, а `MouseShoting` получил сериализованную ссылку:

```csharp
[SerializeField] private Transform muzzle;
```

Точка создания изменена с позиции самой пушки на позицию конца ствола:

```csharp
GameObject projectile = Instantiate(
    projectilePrefab,
    muzzle.position,
    Quaternion.identity
);
```

Направление снаряда по-прежнему задаётся через рассчитанный в `RotateToMouse()` вектор:

```csharp
projectile.transform.rotation =
    Quaternion.FromToRotation(Vector3.up, aimDirection);
```

Так пуля визуально вылетает из ствола, а не из позиции объекта `Gun`, как в предыдущем варианте.

### Проверка шага

Нужно проверить выстрелы вправо, влево, вверх и вниз. `Muzzle` должен вращаться вместе с пушкой и оставаться на конце ствола после отражения спрайта.

## Шаг 5. Подключить шкалу HP врага

Сначала создаётся представление здоровья, которым затем сможет пользоваться `Zombie`. Добавлен компонент `EnemyHp`, адаптирующий игровые значения к стандартному `Slider`:

```csharp
public class EnemyHp : MonoBehaviour
{
    [SerializeField] private Slider hpSlider;

    public void UpdateHp(int hp, int maxHp)
    {
        hpSlider.maxValue = maxHp;
        hpSlider.value = hp;
    }
}
```

В `Enemy.prefab` добавлена иерархия world-space UI:

```text
Enemy
└── Canvas
    └── HPSlider
        ├── Background
        └── Fill Area
            └── Fill
```

Префаб связывает `EnemyHp.hpSlider` с компонентом `Slider`. Состояние здоровья при этом остаётся в `Zombie`, а UI только отображает полученные значения.

## Шаг 6. Добавить зомби здоровье и смерть

Раньше `Zombie` предоставлял только контактный урон. Теперь он владеет полным циклом своего здоровья:

```csharp
[SerializeField] private int maxHp;
[SerializeField] private EnemyHp healthUI;

private int hp;
```

При запуске текущее здоровье инициализируется максимальным:

```csharp
hp = maxHp;
healthUI.UpdateHp(hp, maxHp);
```

Метод получения урона ограничивает урон оставшимся здоровьем, обновляет UI и проверяет смерть. Ниже показана промежуточная часть метода; анимация и частицы добавляются на шаге 8:

```csharp
public void TakeDamage(int damage)
{
    if (damage > hp)
        damage = hp;

    hp -= damage;
    healthUI.UpdateHp(hp, maxHp);

    if (hp == 0)
        Die();
}
```

```csharp
private void Die()
{
    Destroy(gameObject);
}
```

Таким образом, решение об уничтожении принадлежит самому `Zombie`, а `Projectile` только передаёт урон. Это позволяет нескольким попаданиям постепенно уменьшать HP.

Для защиты от отрицательного урона его нужно сначала нормализовать, а затем ограничить итоговое HP снизу:

```csharp
damage = Mathf.Max(0, damage);
hp = Mathf.Max(0, hp - damage);
```

В префабе `Zombie.healthUI` связан с новым `EnemyHp`, а значение `maxHp` установлено в `10`.

### Проверка шага

При создании врага шкала должна быть заполнена полностью. Прямой тестовый вызов `TakeDamage(1)` должен уменьшить её на единицу, а суммарный урон в десять единиц — удалить весь объект врага вместе с дочерним Canvas.

## Шаг 7. Сделать снаряд источником попадания

После появления API `Zombie.TakeDamage()` у `BoxCollider2D` префаба `Projectile` включается `Is Trigger`, а в скрипт добавляется обработчик:

```csharp
private void OnTriggerEnter2D(Collider2D other)
{
    Zombie zombie = other.gameObject.GetComponent<Zombie>();

    if (zombie != null)
    {
        zombie.TakeDamage(damage);
        Destroy(gameObject);
    }
}
```

Распределение ответственности здесь корректное:

- `Projectile` знает величину урона и определяет факт попадания;
- `Zombie` самостоятельно изменяет собственное здоровье и решает, когда умереть;
- пуля удаляется после успешного попадания.

В текущей конфигурации событие может сработать благодаря `Rigidbody2D` на зомби: для 2D-trigger хотя бы один участник должен иметь `Rigidbody2D`. На самой пуле `Rigidbody2D` пока отсутствует, а движение выполняется через `transform.Translate()`.

Для более устойчивой версии следует защититься от повторной обработки до конца кадра и поддержать коллайдеры на дочерних объектах врага:

```csharp
private bool hasHit;

private void OnTriggerEnter2D(Collider2D other)
{
    if (hasHit)
        return;

    Zombie zombie = other.GetComponentInParent<Zombie>();

    if (zombie == null)
        return;

    hasHit = true;
    zombie.TakeDamage(damage);
    Destroy(gameObject);
}
```

Для быстрых пуль стоит добавить `Rigidbody2D`, установить `Gravity Scale = 0`, включить непрерывное обнаружение столкновений и перемещать снаряд средствами физики.

## Шаг 8. Добавить визуальную обратную связь попадания

В `Zombie` появились ссылки, получаемые при запуске:

```csharp
animator = GetComponent<Animator>();
bloodEffect = GetComponentInChildren<ParticleSystem>();
```

После получения урона запускаются trigger аниматора и система частиц:

```csharp
animator.SetTrigger("isHit");
bloodEffect.Play();
```

В `Enemy.controller` добавлены:

- параметр-trigger `isHit`;
- состояние `EnemyHit`;
- переход `Any State → EnemyHit` по `isHit`;
- обратный переход `EnemyHit → EnemyRun` по времени выхода.

Новый клип `EnemyHit.anim` содержит один ключ спрайта, длится один кадр и имеет включённый loop. В префаб врага также добавлена незакольцованная дочерняя `Particle System` с отключённым `Play On Awake`; её сериализация составляет основную часть большого diff префаба.

### Проверка шага

При каждом несмертельном попадании должны одновременно обновляться HP, запускаться hit-анимация и частицы. После реакции враг должен вернуться в `EnemyRun`. Длительность однокадрового зацикленного клипа вместе с переходом по `Exit Time = 0` нужно обязательно проверить в Play Mode. При смертельном попадании `Enemy` уничтожается в том же кадре, поэтому его дочерняя система частиц может исчезнуть прежде, чем эффект станет виден.

## Шаг 9. Связать сцену и префабы

Кодовые изменения начинают работать только после настройки сериализованных ссылок. Текущий diff выполняет следующие соединения:

- `Farmer → AmmoUI`;
- `AmmoUI → AmmoText`;
- `MouseShoting → Muzzle`;
- `Gun → AudioSource` и аудиоклип;
- `Zombie → EnemyHp`;
- `EnemyHp → Slider`;
- `Zombie → Animator` через компонент на том же объекте;
- `Zombie → ParticleSystem` через дочерний объект;
- `Projectile.BoxCollider2D.isTrigger = true`.

Изменение `neodgm SDF.asset` связано с заполнением динамического атласа TextMesh Pro: размер текстуры вырос с `1×1` до `1024×1024`, добавились таблицы символов, включая цифры, и большой блок данных текстуры. Это сопровождающее изменение UI, а не отдельная игровая механика.

## Технические замечания к текущему diff

Эти пункты не отменяют реализованную последовательность, но важны перед следующим коммитом:

1. Новые `.cs`, `.meta` и `EnemyHit.anim` должны быть добавлены в Git вместе. Без `.meta` Unity создаст другие GUID, и сериализованные ссылки сломаются.
2. `Projectile` пока движется изменением `Transform` и не имеет собственного `Rigidbody2D`. Для высокой скорости это менее надёжно, чем физическое движение с непрерывным обнаружением столкновений.
3. Текущий обработчик пули ищет `Zombie` только на объекте конкретного коллайдера и не имеет защиты от повторного попадания в одном кадре.
4. Пуля игнорирует объекты без `Zombie`, включая стены, и продолжает движение до попадания во врага либо истечения `lifetime`.
5. На смертельном попадании `bloodEffect.Play()` вызывается непосредственно перед `Destroy(gameObject)`, поэтому дочерний эффект может не успеть отобразиться. Для гарантированного эффекта его следует отделить от уничтожаемого объекта или сначала завершить реакцию смерти.
6. Однокадровый `EnemyHit.anim` зациклен, а обратный переход имеет `Exit Time = 0`; фактическую длительность реакции следует проверить в Play Mode.
7. `Farmer.OnCollisionEnter2D()` по-прежнему напрямую уничтожает столкнувшегося зомби после нанесения урона игроку. Поэтому уничтожение врага пока не полностью централизовано в `Zombie.Die()`.
8. `transform.parent.GetComponent<SpriteRenderer>()` работает только пока `Gun` является непосредственным ребёнком `Player`. Промежуточный `GunPivot` приведёт к отсутствующей ссылке.
9. В `PlayerMovement` остались закомментированный блок отражения и неиспользуемое поле `SpriteRenderer sr`; после проверки механики их лучше удалить.
10. Имя `MouseShoting` содержит опечатку. Переименование в Unity нужно выполнять вместе с файлом и сохранением соответствующего `.meta`, чтобы не потерять ссылку в сцене.
11. `ChangeBullets(int amount)` допускает отрицательный итог при вызове из другого места. Граница `Mathf.Max(0, bullets + amount)` сделает инвариант явным.
12. `Zombie.Start()` предполагает, что `healthUI`, `Animator` и дочерняя `ParticleSystem` существуют. Для переиспользуемого префаба полезны сериализованные ссылки или проверки с понятной диагностикой.
13. В рабочем дереве есть пробелы в концах строк и предупреждения о преобразовании LF в CRLF. На механику это не влияет, но создаёт шум в ревью.

## Рекомендуемый порядок ручной проверки

1. Запустить сцену и убедиться, что HUD сразу показывает HP и `222` патрона.
2. Перемещать курсор вокруг персонажа, проверяя поворот пушки и отражение персонажа на левой полуплоскости.
3. Выстрелить в четырёх направлениях и убедиться, что пуля появляется у `Muzzle`, звучит выстрел и уменьшается боезапас.
4. Несмертельно попасть в зомби и проверить удаление пули, уменьшение шкалы HP, hit-анимацию и частицы.
5. Нанести суммарно десять единиц урона и проверить уничтожение зомби только при нулевом HP; отдельно зафиксировать, видна ли реакция на смертельное попадание до удаления объекта.
6. Израсходовать все патроны и убедиться, что последующие клики не создают снаряд и не воспроизводят звук.
7. Проверить несколько зомби и попадание на границе двух коллайдеров, чтобы обнаружить возможную повторную обработку.

## Вывод

Главный результат diff — не отдельная функция, а замкнутый цикл взаимодействия: игрок получает отображаемый ресурс, расходует его при выстреле, снаряд передаёт урон владельцу здоровья, а враг самостоятельно обновляет состояние и визуально подтверждает попадание. Логика в целом распределена по подходящим объектам; следующий этап — сделать связи менее зависимыми от иерархии и перевести движение снаряда на более надёжную физическую модель.
